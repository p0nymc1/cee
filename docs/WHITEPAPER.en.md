# Cognitive Execution Engine (CEE) — Technical Whitepaper

> 中文版：[WHITEPAPER.md](WHITEPAPER.md)

> Reshaping how agents execute: from probabilistic trial-and-error to deterministic engineering.

**This document lives in the same repo, under the same version control, as the code.** Every number is reproducible
via `go run ./cmd/cee bench`, `make stats`, or CI. Every claim of "built" links to code or a test. Anything not yet

## Abstract

Today's LLM-based agents hit serious limits in long-running, high-concurrency, cost-sensitive enterprise settings. CEE
abandons the "LLM decides everything" paradigm and proposes a layered architecture — **deterministic intent routing +
edge LLM injection + environment rehearsal sandbox** — that returns execution control to a deterministic state machine
and demotes the LLM to an edge tool that extracts and never decides.

Unlike the common approach, CEE is not Temporal plus a vector database plus a cloud sandbox glued together. It
**pins down the protocol first, then makes every layer's backend replaceable**. The current kernel has **zero external
dependencies** (`go.mod` has no `require` entries): 11,566 lines of Go, 26 packages, 251 tests (plus 17 satellite
module tests), and `go build` completes on an offline machine running Go 1.26+.

> The figures in this section are generated by `make stats`, never hand-written — a whitepaper whose own numbers do
> not reconcile is not persuasive.

## Chapter 1 — Background and industry pain points

### 1.1 Four hard problems with today's agents

Mainstream agent engineering (Prompt → Context → Harness → Loop → Self-Harness → Environment) is essentially
"putting clothes on a large model":

1. **Cost sink**: even trivial tasks burn tokens on chain-of-thought reasoning.
2. **Loss of control**: LLM randomness makes the system a black box, prone to infinite loops.
3. **Fragile memory**: the context window has a physical ceiling and cannot carry a task across cycles.
4. **Late correction**: relying on self-correction after failure makes fault tolerance extremely expensive.

### 1.2 A commonly overlooked fifth point

Those four are industry consensus. But what actually stops enterprises from turning automation on is often the fifth:

> **A correct judgment can still have a catastrophic execution.**

Security teams don't refuse automated containment because they fear a false positive. They fear it being **right** —
blocking the source IP of a password spray, where that IP is the company's own VPN egress, and 900 remote workers drop
off instantly. This class of incident has nothing to do with model intelligence. No smarter model prevents it.

CEE treats this as a first-class concern: **rehearse before executing, rather than reflecting after**.

## Chapter 2 — Core architecture

Four logical layers, mapped one-to-one onto code:

| Layer | Code | Responsibility |
|---|---|---|
| Intent routing | [`intentrouter`](../intentrouter/router.go) | Natural language → pre-registered intent, isolated per domain, never searching across domains |
| Deterministic execution engine (DEE) | [`execution`](../execution/engine.go) | Walk the step DAG: sandbox gating, circuit breakers, suspend/resume, compensation |
| Edge LLM injector | [`llminjector`](../llminjector/injector.go) | The only place an LLM is allowed to run, and only for text → field extraction |
| Pre-execution sandbox | [`sandbox`](../sandbox/sandbox.go) | Simulate a step with side effects once, before it runs |

### 2.1 Technology choices: protocol first, backends second

Documents like this usually enumerate a tech stack. CEE does the opposite — **the kernel binds to no backend**. Each
layer exposes an interface, and heavyweight implementations go into independent satellite modules:

| Interface | Kernel default | Replaceable with |
|---|---|---|
| `intentrouter.Vectorizer` | Lexical Jaccard (zero-dependency) | Any OpenAI-compatible embedding endpoint ([`embedhttp`](../embedhttp/embedhttp.go)), any vector database |
| `llminjector.Extractor` | Domain self-registered function | Any OpenAI-compatible chat endpoint ([`llmhttp`](../llmhttp/llmhttp.go)) |
| `execution.Prober` | In-process call | Local container ([`satellites/dockersandbox`](../satellites/dockersandbox)), remote/cloud sandbox ([`satellites/httpsandbox`](../satellites/httpsandbox)), E2B, … |
| `execution.Action` | Domain Go hook | WASM sandbox ([`satellites/wasmhooks`](../satellites/wasmhooks)), for untrusted third-party code |
| `execution.Store` | In-memory | Durable ([`filestore`](../filestore/filestore.go)), a database |

**Normative handbook rule 1.5** requires the core module to depend only on the standard library; any implementation
needing a heavyweight SDK must live in a satellite module with its own `go.mod`. Because `go build ./...` does not
descend into satellite directories, satellite dependencies are **physically unable** to reach the core.

The practical benefit: anyone can `go get` and immediately `go build` without trusting, auditing, or fetching any
third-party code. For enterprise security review, that is a far stronger statement than "we integrated best-in-class
components."

### 2.2 The engine knows references, not content

The four components exchange only the seven fixed shapes defined in [`entities`](../entities/entities.go). They never
pass an unagreed map. That is what lets any industry's business logic plug in as a domain plugin without one line of
engine change.

A "living document" test enforces this: the two-domain test in `registry_test.go` requires that after any engine
change, two domains with entirely non-overlapping vocabularies still coexist — and that nobody adds an
industry-specific branch to the engine just to make the test pass.

## Chapter 3 — What's different

### 3.0 Positioning: a compiler, not an interpreter

The fundamental difference between CEE and an agent is not *whether* a model is used, but **when the model works**.

An agent reasons **at runtime**: do the same thing ten thousand times and it reasons ten thousand times. And its plan
exists only during execution — there is nothing to review beforehand.

CEE reasons once, **at design time**. The model's output is not an action but a manifest: readable, statically
checkable, replayable against historical data, approvable by a human. After that the process executes
deterministically, at zero model cost, and Tuesday does not produce a different answer from Monday.

> **An agent is an interpreter. CEE is a compiler.**

This is not about sending the model away. Turning a messy paragraph of human speech into a correct process is much
harder than following that process — and that is exactly what the model should be doing. It just should not do it ten
thousand times.

`cee draft` (see 3.7) implements this path.

### 3.1 Decision paradigm: state-machine driven

The normal path is entirely defined by code; the LLM takes no part in flow decisions. The engine closes the set of
step shapes at the type-system level — the `Step` interface has an unexported method, so **only `LeafStep`,
`CompositeStep` and `ParallelStep` in this package can satisfy it**, and no outside package can add a fourth. What is
closed is the set itself, not its size: adding a shape means changing the engine and passing the engine's tests, not
a plugin slipping one in from outside.

Circuit breaker policies must be **registered by name**; hand-written retry loops inside actions are forbidden. That
way "how many safety nets exist in this system, and where does each fall back to" can be audited from one policy
table.

### 3.2 Rehearsal beforehand, not reflection afterwards

Sandbox probes run **before** the real action, read-only. If a probe refuses, the action never executes; the circuit
breaker routes to a human and carries the refusal reason along.

Real output (from the live evidence page):

```
ALERT  password spray against the vpn gateway
       peer=203.0.113.11 host=vpn-gw01 confidence=0.97
       (the 'attacker' address is our own VPN egress)
  -> matched network-detection.T1110_password_spray (1.00)
  -> held for an analyst: containment would have hit something it must not
     because: 203.0.113.11 is our VPN concentrator — about 900 remote workers egress here — blocking it hits us, not the attacker
     trace: [require_confidence select_response contain hold_for_analyst]
```

### 3.3 Waiting is not failure: state persistence across cycles

When a process must wait for an external event (human approval, a maintenance window, a callback), the action returns
`*Suspended`. The engine archives the run, returns a `crypto/rand` resume pointer, and **returns normally** — parking
is not an error, and the circuit breaker never sees it.

`Engine.Resume(pointer, resolution)` merges the external decision into the archived context and continues from the
step after the suspension point. Paired with [`filestore`](../filestore/filestore.go) it survives a process restart.

Three safety guarantees: the pointer is single-use (`Consume` claims it atomically, so an approval cannot be
replayed); claiming is two-phase (the claim is held until `Release`, so a crashed run can be found via `Orphaned()`
rather than vanishing); and suspending with no `Store` configured **errors loudly** rather than silently degrading.

### 3.4 An extraction is a guess, not a fact

This reinforces "the LLM may extract but not decide." Clipping decision fields does not stop the model from
**reading one number wrong** — an extractor that reads $50,000 as $5,000 decided nothing, and yet decided everything.

So `Injector.Extract` **structurally** stamps every field it produces with its provenance
(`ExtractionResult.ModelDerived`); the extractor cannot exempt itself. Consequential steps use
`std.require_verified` to declare which fields will not accept a guessed value.

Confidence scores are deliberately not used: **a model's self-reported confidence cannot be audited by the engine, and
a number nobody can verify is worse than no number — it manufactures false comfort.**

### 3.5 Compensation: undoing side effects that already happened

Probes handle "don't do that action," but have nothing to say about "step 4 failed and the first three already moved
money." A `LeafStep` may declare `compensate_with`, and when a run is abandoned they are undone **in reverse order**.

A failed compensation is never retried and never swallowed — it surfaces in the error as `COULD NOT UNDO`. The action
happened, undoing it also failed, and the world is in a state nobody chose. That is the worst outcome the engine can
report.

### 3.6 Cashing in determinism: replay and regression diff

**This is the one capability nobody else can offer.** Determinism's unique dividend is "the same input necessarily
produces the same output," and it is only worth anything once cashed in:

Real output from `go run ./examples/rule_change`:

```
Last quarter, under the rule in force (auto-approve at or under $100):
  37 refunds -- 29 paid, 8 held

Proposed change: tighten the limit to $50.
Replaying the same 37 refunds against the new rule:
  15 of 37 decisions flip

    r-0005   $63     paid -> held
    ...

  6 more were held before and are held now -- the outcome stands, only the reason changed.
```

**Change one rule, and compute which of last quarter's decisions would flip.** Temporal has durable retries, Airflow
has scheduling — but only a deterministic engine can do this.

Two details decide whether that number can be trusted. First, **a flipped decision and a reworded explanation are
counted separately** — those 6 did not change outcome, and folding them in would report 21 where the truth is 15.
Second, one refund inside the flip range did not flip: **probe verdicts come from the recording, not a live check**,
so an account closed at the time is still closed. The outside world is pinned; only the rule moved.

`Compare` sorts its differences by field name. That sounds minor, but a tool built to demonstrate determinism whose
own output order depends on map iteration demonstrates nothing — pinned by
`TestCompareOrdersDifferencesTheSameWayEveryTime`.

Implementation needs no engine change: probes and extraction are the only entry points for non-determinism, so
[`replay`](../replay/replay.go) records and replays them by wrapping `Prober` and `llminjector.ResultObserver`. A side
benefit is that it catches actions that violate the determinism contract — neither the rules nor the verdicts changed,
yet the result drifted.

### 3.7 Model-drafted workflows (`cee draft`)

```bash
cee draft "expenses over ten thousand need manager approval; never pay out on a closed account"
```

The model composes a manifest from a **closed action vocabulary** (`std.*` plus registered hooks), then passes four
gates:

1. **A manifest describes shape and can never smuggle in behaviour** — the worst the model can produce is a wrong
   arrangement of actions that already exist and have already been reviewed.
2. **Invented actions do not get through** — `Validate` warns and `Load` refuses to bind names that exist in neither
   the standard library nor the hooks.
3. **Warnings alone are not a pass** — `Validate` cannot see a domain's Go hooks, so a draft claiming to need no hooks
   is additionally run through `Load`, turning "only warnings" into a real guarantee.
4. **The correction loop has a hard ceiling** — feeding validation errors back to the model is useful, but **an
   unbounded correction loop is precisely the failure mode this project exists to eliminate**. `MaxAttempts` is a hard
   cap; a draft that never passes is reported honestly rather than returned.

The CLI only prints; it never saves. A draft is a proposal, and the entire point of moving the model to design time is
that a person reads it first.

This also removes CEE's most concrete adoption cost — **you no longer have to work the process out yourself first**.

## Chapter 4 — Current state and roadmap

### 4.1 Done (with code and tests)

| Capability | Location |
|---|---|
| Four-layer core architecture | `intentrouter` / `execution` / `llminjector` / `sandbox` |

| Static validator (cycle detection, reachability, dangling references) | `manifest.Validate`, `cee validate` |
| No-code (L1) standard action library | `stdlib` (`std.set`/`require`/`rule_check`/`suspend`/`require_verified`) |
| Suspend/resume + durable store | `execution` + `filestore` |

| HTTP surface | `httpapi` (a mountable `http.Handler`) |
| Model-drafted workflows | `draft` / `cee draft` |
| Provenance stamping and verification gating | `entities.ModelDerived` + `std.require_verified` |
| Replay and regression diff | `replay` / `examples/rule_change` |
| Parallelism and joins (fan-out / fan-in) | `execution/parallel.go`, manifest `type: "parallel"` |
| Metrics and benchmark leaderboard | `scorecard` / `bench` / `cee bench` |
| Community plugin catalog | `catalog` / `cee list`·`lint`·`install` |
| Real model backends (zero-dependency) | `llmhttp` / `embedhttp` |
| Satellite module templates | `satellites/dockersandbox`, `satellites/httpsandbox`, `satellites/wasmhooks` |

All six meta-scenarios have landed as runnable examples: security monitoring, approval flows, ticket routing,
scheduling, data sync, anomaly monitoring — plus two real cases (network intrusion detection, crypto market
surveillance).

### 4.2 Not done, in priority order

1. **Wiring a real identity source**: `httpapi` provides an `Identify` hook and denies unconfigured deployments by
   default; engine-side authorisation is in place (audience + `Authorizer`, deny by default, a refusal does not
   consume the pointer, the approver is recorded as `cee.resumed_by`). What's missing is connecting it to a real
   **JWT / mTLS / session** — that belongs to the integrator, but a reference implementation is missing.
2. **Validating the drafting path against a real model**: `draft`'s logic and all four gates are tested (with stubs,
   offline), but "does the model get it right the first time" has not been measured against a real endpoint.
3. **Suspension TTL and escalation**: waiting has no end. "Escalate if nobody approves within three days" is a routine
   approval-flow requirement that currently cannot be expressed.
4. **Diagnostic metrics**: `scorecard` measures output (deterministic steps, calls eliminated), not error (intent miss
   rate, probe refusal rate, escalation-to-human rate). **Measuring only the flattering numbers is a form of bias.**
5. **Visual orchestration**: `cee draft` provides a natural-language entry point; a drag-and-drop interface is still
   missing. The substrate is pure JSON and statically checkable, so a frontend can come later.

### 4.3 The biggest risk is not in the code

All five items above are engineering problems with known solutions. The real risk is something else: **the catalog
currently holds 2 plugins, both samples written by the author, and there are no third-party entries on the
`cee bench` leaderboard.** The no-code contribution tier, the standard action library, the distribution catalog, the
determinism leaderboard — the whole community flywheel is **architecturally ready and has zero fuel**.

Protocols win by adoption, not by quality. The engineering quality of this artifact is far ahead of its distribution,
and that gap will not close on its own.

## Chapter 5 — How things are measured

### 5.1 Measured numbers

Current `cee bench` output (reproducible):

```
rank plugin           determinism  events     errors   LLM calls eliminated vs agent
1    access-review    100%         4          0        8 of 8
2    sla-guard        100%         4          0        8 of 8
```

Basis: taking "a naive agent that calls the model once per step" as the baseline, we count how many calls CEE
eliminated. **No token estimation** — an estimate cannot be verified, and putting one in a report collapses at the
first follow-up question.

### 5.2 Targets (not yet measured; must not be cited as results)

- Intent routing hit rate > 85%
- Normal-path cost down > 80% versus a baseline agent
- Response latency in the millisecond range

All three require real production traffic and a controlled experiment. The current code **has no mechanism for
measuring intent hit rate** (see 4.2 item 6), which must be built before that number can exist.

- **Not applicable** when a process genuinely needs open-ended reasoning — CEE's entire design is built to keep the

- CEE's differentiation is in exactly one place: **deterministic processes that contain irreversible operations and
  need auditing and retrospection.**

## Chapter 7 — Relationship to the open-source ecosystem

CEE does not reinvent components, and does not pre-bind them. It defines **the connection protocol and the layer
boundaries**, leaving backend choice to the integrator:

- Need distributed orchestration → wrap Temporal in a satellite module; the core does not change
- Need vector retrieval → implement `Vectorizer`, connect Qdrant or any embedding service
- Need strong sandbox isolation → implement `Prober`, connect E2B, a container, or WASM

**A permanently dependency-free core is a hard rule, not a phase** (handbook 1.5). Any PR adding a `require` to the
root `go.mod` is rejected.

## Chapter 8 — Summary

As model capabilities converge, the moat is no longer a well-written prompt. It is **who can push AI capability into
core enterprise systems at scale, at lower cost and with higher certainty.**

CEE does not chase model omniscience; it chases reliability and auditability at the execution layer. Each of its three
claims is backed by code and tests rather than rhetoric:

1. **Decisions belong to code** — the LLM only extracts, and extractions carry provenance so a guess cannot pass as a
   fact.
2. **Dangerous actions are rehearsed first** — a read-only probe runs before execution; a refusal escalates to a human
   with the reason attached, and side effects that already happened can be compensated in reverse order.
3. **Determinism must be cashed in** — before you change a rule, compute which decisions it would change.
